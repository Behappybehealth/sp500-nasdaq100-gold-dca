## 每条问题的四段工作流

```
① 梳理  ── 我写：现在会发生什么 / 为什么 / 怎么修 / 为什么有效 / 怎么验证 / 业界做法
     ↓
② 确认  ── 你拍板修复路径 → 回填「✅ 确认记录」（含你选了哪条路、为什么）
     ↓                          ⚠️ 没有这一步，不许动代码
③ 修复  ── 施工 → 回填「🔧 实际修复」（改了哪些 file:line、commit）
     ↓
④ 验证  ── 跑验证脚本 → 回填「✔️ 验证结果」（贴真实输出，不贴"应该没问题"）
```

**状态标记**：🔴 待确认 · 🟡 已确认待修 · 🟠 修复中 · ✅ 已验证 · ⚪ 已判定不修

**编号规则**：`BUG-0XX` 全局唯一、只增不改、**永不复用**。问题一旦登记就不删除 —— 即使成因消失（比如承载它的文件被删了），也留在册上标 ✅ 并写清是被谁连带修掉的。

**行号坐标约定**：本文所有 `file:line` 都是**记录当时的坐标**（登记日的现场 / 修复日的落点），**不是指向当前代码的活链接**。所以一律写成不可点击的等宽文本 —— 代码一重构行号就漂，而回头把它改成"修好后的位置"等于篡改证据。要看当时的原文：`git show <该条目的 commit 或其父提交>:<file>`。**"当前代码在哪"由 [ARCHITECTURE-DETAIL.md](ARCHITECTURE-DETAIL.md) 负责**（活文档，锚点 + 行号双写、每节末尾标复核日期）。最容易踩空的一处：`app.py` 于 2026-08-18 经 `BUG-020` 七刀从 1984 行收口为 66 行纯装配层（拆分前最后一版 `77ea4a6`），因此 2026-08-18 及之前的条目里凡 `app.py:` 三位数以上行号，那段代码现已在 `src/` 下。

## BUG-001｜跨用户数据串号

| 等级 | 状态 | 发现日期 | 确认日期 | 修复日期 | 主要证据 |
|---|---|---|---|---|---|
| **P0** | ✅ 已验证 | 2026-08-17 | 2026-08-18 | 2026-08-18 | `app.py:556-557`、`storage.py:368` |

### ① 现在会发生什么

用户 A 登录看完今日建议，15 分钟内用户 B 登录 —— **B 看到的持仓、市值、浮盈亏、年化收益、今日建议金额，全都是 A 的。**

不是"泄露一点点"，是 B 的整个决策建立在 A 的持仓上。**B 会照着这个金额真去下单。**

### ② 为什么会这样（原理）

**两个独立原因，任一个都足以串号。**

**原因一：缓存是"整个服务器共用的一块白板"**

```python
app.py:556   @st.cache_data(ttl=900, show_spinner=False)
app.py:557   def run_model(amount: float | None) -> dict:
```

`@st.cache_data` 的意思是"记住这个函数的结果，900 秒内同样参数直接返回"。它判断"同样参数"的依据，**只看函数的参数列表** —— 这里只有 `amount` 一个。

```
A 调用 run_model(None) → 算出 A 的结果 → 写到白板上，标签写「None」
B 调用 run_model(None) → 一看白板上有「None」→ 直接把 A 的结果抄给 B
```

**关键区别**（也是 ARCHITECTURE §1.2 里那句最要紧的话）：

| 机制 | 作用域 | 这个项目怎么用的 |
|---|---|---|
| `st.session_state` | **每个浏览器一份** | 存登录状态，所以每人的"我是谁"是对的 |
| `st.cache_data` | **整个服务器进程共用一份** | 存模型结果，所以每人的"我的持仓"是错的 |

登录状态是对的、决策结果是错的 —— 这就是为什么这个 bug 看起来很难相信：**页面右上角明明显示着 B 的名字。**

**原因二：所有用户共用同一个数据文件**

```python
app.py:26-34    BASE = --base-dir 指定的目录，没指定就是项目目录
                DATA_DIR = BASE / "data"
                ↑ Cloud 上没人传 --base-dir，所有用户都是同一个 data/
storage.py:368  sync_local(user)：把这个用户的成交记录写进 data/transactions.csv
app.py:549-552  每个会话首次进入时调用 sync_local(CURRENT_USER)
app.py:561-562  run_model 把 --base-dir str(BASE) 传给子进程
```

A 登录时把 A 的账本写进这个文件；B 登录时把它**整体覆盖**成 B 的账本。两人同时在线，就是**两个子进程在读一个正在被对方覆写的文件**，竞态窗口是整个 sync + 计算过程（数秒到数十秒）。

**为什么引擎帮不上忙**：引擎是 subprocess 起的（§1.3），它**根本不知道谁是当前用户** —— 只知道 `--base-dir` 指向哪、那个目录里的 CSV 写了什么。谁最后写的它就算谁的。

### ③ 怎么修

**必做（小改动，堵住原因一）** —— 让缓存键包含用户身份：

```python
# 现在：缓存键 = (amount,)
@st.cache_data(ttl=900)
def run_model(amount): ...

# 改成：缓存键 = (amount, user, data_dir)
@st.cache_data(ttl=900)
def run_model(amount, user, data_dir): ...   # user/data_dir 参与键，即使函数体不直接用
```

**该做（堵住原因二）** —— 每个用户一个数据目录：

```
data/
├── users/
│   ├── alice/transactions.csv      ← A 的账本
│   └── bob/transactions.csv        ← B 的账本
└── market_history/                 ← 行情缓存共享（这个共享是对的）
```

然后 `run_model` 传 `--base-dir data/users/<用户名>`。

**⚠️ 待你拍板的岔路（这是本条的核心待确认项）**

| 方案 | 做法 | 改动量 | 优点 | 代价 |
|---|---|---|---|---|
| **A · Cloud 单实例多目录**（我推荐） | 缓存键加用户 + `BASE` 推导改成 `data/users/<user>` | ~40 行，全在 app.py | 引擎保持纯净、仍可离线单跑；不动项目最干净的那道边界 | 本地仍有 CSV 中间层，多一层要维护 |
| **B · 引擎直接读 Sheets** | 去掉本地 CSV 落盘，引擎自己连 Sheets | 大，跨 3 个文件 | 一次性根治"共享文件"这件事 | **把 §1.3 那道最干净的边界弄脏** —— 引擎从此依赖网络和凭据，再也不能离线单跑，回归测试变难 |

### ④ 为什么这么修有效

**缓存的第一原则：缓存键必须包含所有会影响结果的输入。**

现在"用户身份"影响结果，却不在键里 → 系统认为"参数一样，结果就该一样" → 必然串号。把用户加进键，A 和 B 就是白板上两个不同的格子，各存各的。

**数据目录分开的原理**：两个进程写同一个文件必然竞争，写不同文件就不会。行情缓存留在共享位置是**刻意的** —— 行情对所有人是同一个事实，共享既省流量又省磁盘。

### ⑤ 修完怎么验证

1. A 登录记一笔特征明显的成交（比如 12345 元），退出
2. **30 秒内**（远小于 900 秒 TTL）B 登录 → **B 的持仓里不应出现 12345**
3. 检查磁盘：`data/users/` 下应有两个目录，各自 CSV 内容不同
4. 反复交替登录 5 次，两人数字始终各自独立
5. 回归：`.venv/Scripts/python.exe scripts/dca_calculator.py --base-dir .` 仍能单跑并输出 15 个顶层键（确认没弄坏引擎边界）

### ⑥ 业界通用做法

这是**多租户系统**（一套程序服务多个客户）的入门必修课，标准做法两条：

- **缓存按租户隔离**（tenant-scoped cache）：任何缓存键都必须带租户 ID。成熟的缓存库通常**强制**要求传租户上下文，就是为了防这个。
- **数据按租户隔离**：轻量做法是"一租户一目录 / 一 schema"，重量做法是"每行带 `tenant_id` 且所有查询强制过滤"。

> **这个项目在 Sheets 层用了后者**（每张表都有 `user` 列），**但在本地缓存文件层漏了** —— 一半做对了，另一半没做。这种"部分正确"最危险，因为它让人以为已经做过隔离了。

## BUG-002｜一次读取失败 = 全部历史被覆盖

| 等级 | 状态 | 发现日期 | 确认日期 | 修复日期 | 主要证据 |
|---|---|---|---|---|---|
| **P0** | ✅ 已验证 | 2026-08-17 | 2026-08-18 | 2026-08-18 | `storage.py:107-110`、`storage.py:299-307`、`storage.py:378-380` |

### ① 现在会发生什么

Google 那边抖一下（返回 503、配额超了、凭据过期、网络闪断），紧接着你记一笔账 —— **整张成交记录表被这一笔覆盖，几百条历史全没了。而且没有备份可以恢复。**

第二种触发方式更糟：读取失败让系统以为"一个用户都没有" → 登录页变成"首次注册"表单 → **任何访客注册即成为管理员**，同时把 users 表覆盖成只有他一行 → **所有账号消失**。

### ② 为什么会这样（原理）

回到 ARCHITECTURE §1.4：Google Sheets 只能"整张表读下来 / 整张表推上去"。加一行的实际动作是：

```python
storage.py:299-307   def append_row(...):
                         df = _read_ws(table, fields)      # ① 读整张表
                         df = concat([df, 你这一行])        # ② 拼上你的
                         _write_ws(table, df)              # ③ 整张推回去
```

**问题在第 ① 步**：

```python
storage.py:107-110   try:
                         df = _conn().read(worksheet=name, ttl=0)
                     except Exception:
                         return pd.DataFrame(columns=fields)   ← 失败也返回一张空表
```

`except Exception: return 空表` 的意思是 **"读失败"和"表真的是空的"在返回值上完全无法区分**。上层拿到一张空表，就当真的是空的，照常往下走。

**打个比方**：让人去图书馆抄一本书，他没找到书（或者路上摔了），回来跟你说"这本书是空白的"。你信了，在空白纸上写下一行字，交回去把原书换掉了。

**第二根引信（走鉴权路径）**：

```
app.py:542       names = storage.list_users()      ← 读失败返回 []
app.py:540-546   名单为空 → 渲染「首次自举」表单（任何访客都看得到）
app.py:507-510   提交时的防呆：再读一次 list_users_fresh()
                 ↑ 读还在失败 → _fresh 依然是 [] → 防呆失效
storage.py:205   create_user() → _write_ws("users", concat([空表, 新 admin]))
```

**那个防呆只防"会话名单过期"，不防"读失败"。** 两次读都走同一个会把失败变成空表的函数，所以"再读一次"确认不了任何事。

**为什么没有恢复路径**：

| 保护 | 实际情况 |
|---|---|
| Google Sheets 版本历史 | 可能提供平台侧的最后一道恢复机会，但项目没有命名快照、自动导出或经过演练的恢复流程；**不能把“平台也许还能回退”当成项目自己的备份** |
| 本地 `data/*.localbak` | **假保护**。`storage.py:378-380` 的条件是"`.localbak` **不存在时**才备份" → 只在第一次 sync 时生成过一次，**永远是最早那一份** |
| `.localbak` 的写法 | 用 `path.replace()` —— 这是**移动**不是复制。移动完到重新写出之间崩掉，**当前文件就没了** |

### ③ 怎么修

**三层，从内到外：**

**第一层：让失败可见**（这是根治的一刀）

```python
# 现在：读失败 → 空表 → 上层无法区分
except Exception:
    return pd.DataFrame(columns=fields)

# 改成：读失败 → 抛出去
except Exception as e:
    raise SheetReadError(f"读 {name} 失败") from e
```

上层 `append_row` 让异常穿透，UI 显示"存储暂时不可用，请稍后重试"，**不写**。

**第二层：写前快照**

`_write_ws` 之前先把当前表内容复制到另一个 worksheet（如 `transactions_bak_YYYYMMDD`）或导出成本地带时间戳的文件。**先备份，再覆盖。**

**第三层：修 `.localbak`**

```python
# 现在：只在第一次备份 + 用移动
if path.exists() and not 备份.exists():
    path.replace(备份)

# 改成：每次都备份 + 用复制 + 带时间戳 + 保留最近 N 份
shutil.copy2(path, path.with_suffix(f".{时间戳}.bak"))
清理只留最近 10 份
```

**顺带**：`create_user` 的自举分支要加一道独立防呆 —— "只有在**确认读取成功**且结果确实为空时"才允许自举。

### ④ 为什么这么修有效

**核心是一个原则：不要让"错误"伪装成"数据"。**

现在的代码把"我不知道"翻译成了"没有"。这两件事在语义上差了天地：
- "没有" → 可以安全地写入第一行
- "我不知道" → **绝对不能写**

这在工程上叫 **fail-closed**（失效即拦住），和 `BUG-003` 是同一个原则的两种表现。

**为什么"写前快照"是必须的第二层**：第一层堵住的是"已知的一种失败"。但覆盖式写入这个模式本身就是危险的 —— 任何没预料到的路径都可能触发它。快照的价值是**把不可逆操作变成可逆的**。

**为什么 `.localbak` 要改成复制**：`replace()` 在"移动完成"到"新文件写出"之间存在一个窗口，此时磁盘上**一份都没有**。复制则始终保证至少一份完整数据在。

### ⑤ 修完怎么验证

1. **模拟读失败**：临时把 `_conn()` 改成直接 `raise`，然后点"记一笔账" → 应该看到明确的错误提示，**且 Sheets 里的数据一行都没变**
2. **模拟读失败 + 空名单**：同上，打开登录页 → **不应**出现"首次注册"表单，应该是"存储不可用"
3. **验证快照**：正常记一笔账 → 检查是否生成了带时间戳的快照，且内容是**写之前**的状态
4. **验证 `.localbak` 滚动**：连续同步 3 次 → 应有 3 份带不同时间戳的备份，且原文件始终存在
5. **恢复演练**（最重要）：故意破坏一张表，然后**真的用快照恢复一次**。没演练过的备份等于没有备份

### ⑥ 业界通用做法

- **区分 "empty" 和 "error"**：这是 API 设计的基本纪律。`Optional[T]` / `Result<T, E>` / 抛异常，任选一种，但**绝不能用同一个值表示两件事**。
- **读改写要有并发保护**：真数据库用事务 + 乐观锁（`WHERE version = N`）。表格没有这个能力，所以只能靠"写前快照"补。
- **备份的三个硬要求**：① 有调度（不是手动）② 有多个时间点（不是只留一份）③ **验证过能恢复**。三条缺一条就不叫备份。业界叫 3-2-1 原则。
- **不可逆操作前置确认**：任何"覆盖/删除"级别的操作，要么可回滚，要么需要显式确认。

## BUG-003｜认证是 fail-open 的（门闸可以整体消失）

| 等级 | 状态 | 发现日期 | 确认日期 | 修复日期 | 主要证据 |
|---|---|---|---|---|---|
| **P0** | ✅ 已验证 | 2026-08-17 | 2026-08-18 | 2026-08-18 | `app.py:430-431`、`storage.py:63-68` |

### ① 现在会发生什么

正常时：打开网页 → 要求输入名字和 PIN → 通过才进主界面。

**但如果读取凭据这一步出任何问题** → 登录页**完全不出现**，任何人打开网址直接进主界面，身份是 `"local"`。**页面上看不出任何异常，没有任何报错和日志。**

而应用已经设成 public（否则家人打不开，见 ARCHITECTURE §1.7），**这道门闸是唯一防线**。

### ② 为什么会这样（原理）

```python
app.py:430   CURRENT_USER = "local"
app.py:431   if storage.sheets_enabled():        ← 整个登录门闸在这个 if 的里面
                  ... 名字 + PIN 校验 ...
                  st.stop()                       ← 没登录就停在这里
             # if 结束，下面是主界面
```

而这个开关是：

```python
storage.py:63-68   def sheets_enabled():
                       try:
                           return "gsheets" in st.secrets.get("connections", {})
                       except Exception:
                           return False           ← 出任何岔子都返回「关」
```

`try / except Exception: return False` 的意思是"不管出什么错，都当作没配凭据"。而"没配凭据"在这个项目里等于"单机模式，不需要登录"。

**于是一条完整的失效链：**

```
secrets 读取抛异常（Cloud 后台误删/误改、GCP 凭据过期、st.secrets 任何内部错）
   → sheets_enabled() 返回 False
   → app.py:431 的 if 不成立
   → 门闸那 120 行代码整块不执行
   → CURRENT_USER 保持 "local"
   → 访客直接进主界面
```

**打个比方**：门禁系统的逻辑写成了"如果读卡器坏了，就当今天不需要刷卡"。**断电之后门是自动打开的。**

这在安全工程里有专门的名字：**fail-open**（失效即放行）。反面是 **fail-closed**（失效即拦住）。

**为什么特别难发现**：零日志、零启动断言、UI 上没有任何区别。安全控制朝着**不安全**的方向静默失效 —— 你不会收到任何通知，只有等到有人告诉你"我没登录就进去了"。

### ③ 怎么修

加一个显式的"我要求哪种模式"配置，然后在**程序启动时就检查**：

```python
# 大意（不是最终代码）
AUTH_MODE = 读配置("AUTH_MODE", 默认="sheets")     # sheets | local

if AUTH_MODE == "sheets":
    if not storage.sheets_enabled():
        st.error("配置错误：AUTH_MODE=sheets 但读不到 Google 凭据。已停止。")
        st.stop()                                  # 拦住，不降级
    # 往下必然走登录门闸
elif AUTH_MODE == "local":
    CURRENT_USER = "local"
    st.warning("⚠️ 单机模式：未启用登录")           # 明确、可见、是你选的
```

同时把 `sheets_enabled()` 里的 `except Exception: return False` 改成**区分两种情况**：

- "配置里确实没有 gsheets 这一项" → 返回 `False`（正常的单机模式）
- "读配置时抛异常" → **抛出去**，让上层知道出事了

### ④ 为什么这么修有效

核心是把**一个隐式推断**换成**一个显式声明**。

现在的逻辑是"我猜你想要什么模式"，猜的依据是**文件在不在**。改完是"你必须告诉我要什么模式，然后我检查你给的东西够不够，不够就罢工"。

这叫 **fail-closed**：安全控制失效时，朝着"更安全"的方向倒。门禁断电应该是锁死，不是敞开。

配合的第二个原则是 **fail fast on startup**（启动即校验）：配置问题应该在程序启动的第一秒暴露，不要等到运行时才以奇怪的方式表现出来 —— 尤其不要以"少了一道门"的方式表现出来。

### ⑤ 修完怎么验证

1. 正常配置下启动 → 出现登录页 ✅
2. **故意**把 secrets 里的 `[connections.gsheets]` 改名成 `[connections.gsheetsX]` → 启动应该**立刻报错停住**，而不是进主界面
3. 更狠一点：让 `st.secrets` 直接抛异常（临时改代码模拟）→ 同样必须停住
4. 明确设 `AUTH_MODE=local` → 直进主界面，且页面上有**显眼的**"单机模式"提示
5. 检查：`grep -n "sheets_enabled" app.py` 的所有命中点，确认没有第二处还在用它做安全判断

### ⑥ 业界通用做法

- **Secure by default / fail-closed**：安全机制的默认值和失效方向都应偏向"拒绝"。这是 OWASP 反复强调的第一条。
- **启动期配置校验**（config validation at boot）：把所有必需配置在启动时校验一遍，缺了就拒绝启动。Kubernetes 里叫 readiness probe 失败，12-factor 应用叫 "fail fast"。
- **绝不用「文件是否存在」推断安全策略**：策略必须是显式声明的，**环境的偶然状态不能改变安全模型**。这条是本 bug 的核心教训。

## BUG-004｜PIN 的保护强度撑不住公开部署

| 等级 | 状态 | 发现日期 | 确认日期 | 修复日期 | 主要证据 |
|---|---|---|---|---|---|
| **P0** | ✅ 已验证 | 2026-08-17 | 2026-08-18 | 2026-08-18 | `storage.py:134-135`、`storage.py:190` |

### ① 现在会发生什么

有人拿到 `dca365.streamlit.app` 这个地址（应用是 public 的），打开登录页：

1. **用户名不用猜** —— 登录页的下拉框把所有用户名列给未登录访客看（`app.py:540-546`）
2. **PIN 只有 4 位也行** —— 1 万种组合
3. **试错次数没有上限** —— 无限速、无锁定、无验证码
4. **试错没有任何记录** —— 全项目零日志，你永远不会知道有人试过

因为服务端没有失败限速或锁定，攻击者可以持续自动尝试；穷举 4 位 PIN 最多只有 1 万次请求，实际耗时取决于网络和 Streamlit 每次重跑的速度，但**系统自身没有任何机制让尝试停下来**。进去之后能看到的是**真实持仓金额和成交历史**。

第二条路更快：pin_hash 一旦从 Google Sheet 泄漏（协作者被加、误设公开链接、服务账号被复用），**等于明文** —— 见下面 ②。

### ② 为什么会这样（原理）

| 事实 | 证据 |
|---|---|
| PIN 只要 4–8 位 | `storage.py:190` `if not (4 <= len(pin or "") <= 8)` |
| 哈希是**单轮无盐 SHA256** | `storage.py:134-135` `sha256(f"dca::{name}::{pin}")` |
| 唯一的"盐"是用户名 —— 而用户名在登录页**下拉可枚举** | `app.py:540-546` |
| **零失败限速、零锁定、零审计日志** | grep `attempt` / `lockout` / `rate_limit` / `fail_count` 全项目零命中；`logging` 在三个主文件里零命中 |
| 应用已 public，这是唯一防线 | 为绕开 Streamlit 私有锁改的，见 ARCHITECTURE §1.7 |

**"单轮 SHA256" 为什么是问题 —— 这是本条最需要讲清的一点。**

SHA256 是**为速度设计**的算法（它的本职是校验文件完整性，那里越快越好）。一块消费级显卡每秒能算**几十亿次** SHA256。

```
4 位纯数字 PIN = 10000 种组合
一块 GPU 每秒 ~5,000,000,000 次
   → 全部试完需要 0.000002 秒
```

**4 位 PIN 在 GPU 上是「瞬间」，不是「很快」。** 8 位纯数字（1 亿种）也只要 0.02 秒。

**“盐”是什么、为什么用户名不能替代随机盐**：

盐（salt）是一段每个账号都不同的随机数据，混进哈希里。它的作用不是保密——盐通常就和哈希一起明文存放；它的作用是让攻击者**不能拿一张预先算好的通用对照表批量套所有账号**，而必须针对每个账号的盐重新计算。

```
无盐：同一个 PIN 永远得到同一个 hash，一张通用表可以批量查
随机盐：每个账号的结果不同，必须按该账号的盐重新算一遍
```

这个项目把**用户名**拼进哈希，确实能让不同用户名的结果不同，因此不是“完全没有任何区分”；但用户名是可预测、可枚举且不随机的，攻击者能在拿到哈希之前就针对公开用户名预计算。更关键的是，**无论盐怎么选，单轮 SHA256 都快得离谱**：知道用户名和哈希后，4～8 位 PIN 仍可瞬间穷举。正确做法仍是“每账号随机盐 + 专用慢哈希”，不能把用户名当成合格替代品。

### ③ 怎么修

**三件事，可以分开做：**

**第一件：换成慢哈希**（这一件最重要）

```python
# 现在：一次 SHA256，快得像闪电
hashlib.sha256(f"dca::{name}::{pin}".encode()).hexdigest()

# 改成：PBKDF2 高迭代（Python 标准库自带，无需新依赖）
salt = secrets.token_bytes(16)                     # 真随机盐，每账号一份
key  = hashlib.pbkdf2_hmac("sha256", pin.encode(), salt, 200_000)
# users 表存 salt 和 key 两个字段（都存 hex）
```

`200_000` 是“迭代次数” —— 让计算重复 20 万遍。2026-08-17 在本项目 `.venv` / Python 3.14.4 上实测 8 次中位数约 **0.073 秒/次**；具体机器会不同，因此最终迭代数应按目标服务器重新标定。

**第二件：加失败限速**

users 表加两列 `fail_count` / `locked_until`。连续失败 5 次 → 锁 15 分钟。锁定期间无论 PIN 对不对都拒绝。

**第三件：PIN 位数下限提到 6，并给 `delete_user` / `reset_pin` 加审计行**

**⚠️ 迁移问题（必须一起想）**：现有账号存的是旧格式 hash。方案是 users 表加 `hash_algo` 列，值为 `sha256_v1` 的走旧校验、**校验通过后立刻用新算法重写**（渐进式迁移），全部迁完再删旧分支。

### ④ 为什么这么修有效

**慢哈希的原理是"把攻击者的成本乘以 20 万，把你的成本乘以 20 万"** —— 听起来对称，但结果完全不对称：

| | 现在 | 改后 | 影响 |
|---|---|---|---|
| 你登录一次 | 近乎瞬间 | **本机实测约 0.073 秒** | 通常不影响体验 |
| 离线串行穷举 4 位 PIN | 近乎瞬间 | **本机折算约 12 分钟** | 不再是瞬间，但仍远远不够安全 |
| 离线串行穷举 6 位 PIN | 近乎瞬间 | **本机折算约 20 小时** | 再叠加在线限速，攻击成本显著提高 |

**这就是慢哈希的全部立意**：正常登录只验证一次，穷举却要反复验证成千上万次。同样的倍数，对正常用户只是约十分之一秒，对攻击者会累积成分钟或小时；再配合在线限速，效果才完整。

**真随机盐的价值**：把“拿一张通用预计算表批量收割”变成“拿到每个账号的盐后，再为该账号单独重算”。盐不需要保密；关键是它随机、唯一，攻击者无法在拿到账号记录之前准备一张能通吃所有人的表。

**限速的价值**：慢哈希只把在线爆破从"秒"拖到"小时"；限速直接把它变成"不可能"（5 次/15 分钟 = 一天最多 480 次）。**两者是叠乘关系，都要有。**

### ⑤ 修完怎么验证

1. 注册一个新账号 → 检查 users 表里存的是 `salt` + `key` 两个字段，且 `hash_algo` 标了新算法
2. **同一个 PIN 注册两个账号 → 两个 key 必须完全不同**（这一条直接证明盐生效了）
3. 在**实际部署机器**上基准测试并记录中位数；目标约 0.05–0.3 秒。低于目标要提高迭代数，明显高于目标会影响体验
4. 故意输错 5 次 → 第 6 次应该被拒绝并提示锁定，**即使 PIN 是对的**
5. 等 15 分钟后重试 → 应该恢复
6. **迁移验证**：用一个旧账号（旧 hash）登录 → 应该成功，且登录后 users 表里该行已变成新格式
7. 试着设 5 位 PIN → 应被拒绝

### ⑥ 业界通用做法

- **密码哈希只用为它设计的算法**：argon2id（当前首选）、bcrypt、scrypt、PBKDF2。**通用哈希（SHA256/MD5）用于密码是明确的反模式**，OWASP Password Storage Cheat Sheet 第一条就是这个。
- **每个密码一个独立的随机盐**，且盐不需要保密（存在库里就行），只需要不可预测。
- **限速 + 锁定 + 审计三件套**：慢哈希防离线爆破，限速防在线爆破，审计让你知道有人在试。
- **PIN 这种低熵凭据本身就不该单独扛公开入口**。业界的做法是：要么加第二因素（邮箱/TOTP 验证码），要么把入口收窄（IP 白名单、私有链接、平台层认证）。
- **渐进式哈希迁移**（rehash on login）是标准套路，不需要让用户重设密码。

## BUG-005｜Google 私钥会被打进 Docker 镜像层

| 等级 | 状态 | 发现日期 | 确认日期 | **修复日期** | 主要证据 |
|---|---|---|---|---|---|
| **P0** | ✅ **已验证** | 2026-08-17 | 2026-08-17 | **2026-08-17** | 旧 `deploy/Dockerfile:21`（已删，`git show 574c7a7:deploy/Dockerfile`） |

> **本条由 [`BUG-012`](#bug-012docker-那套从来没跑通过一次却被标唯一事实源) 的修复连带解决** —— 见顶部「🔗 连带修复追溯」。
> **记录保留在册**，因为成因和教训对"将来谁再写 Dockerfile"仍然有效。

### ① 原先会发生什么

只要有人执行一次 `docker build`，**Google 服务账号的私钥就被永久烤进镜像**。之后：

- 镜像推到任何 registry（哪怕是私有的）→ 有 pull 权限的人都能取出私钥
- 镜像分享/导出给任何人 → 私钥跟着走
- 拿到私钥 = 拿到那个 Google 表格的**完全读写权** = 所有人的真实持仓和成交历史

### ② 为什么会这样（原理）

```
.dockerignore 原全文 8 行：
    data/  __pycache__/  *.pyc  .git/  .claude/  backtest*/  *.md  !deploy/
    ↑ 没有排除 .streamlit/

旧 deploy/Dockerfile:21    COPY .streamlit/ .streamlit/        ← 整个目录

开发机实况：.streamlit/secrets.toml 存在，2600 字节，含真实 private_key
```

**关键认知一：`.gitignore` 和 `.dockerignore` 是两份互不相干的清单。**

```
.gitignore     管的是「git 会不会把它提交进版本库」
.dockerignore  管的是「docker build 会不会把它送进构建上下文」
```

`secrets.toml` 在 `.gitignore` 里 → git 护住了。但 `.dockerignore` 里没有 → `docker build` 照样打包。**很多人以为 gitignore 是万能的护身符，它不是。**

**关键认知二：Docker 镜像层是只读堆叠的，删不掉。**

```
Dockerfile 每一条指令产生一"层"，层是只读的，后面的层叠在前面上面。

第 21 层：COPY .streamlit/     ← 私钥在这层里
第 30 层：RUN rm secrets.toml  ← 只是在最终视图里"看不见"了

docker save 镜像 → 解开 → 第 21 层原封不动，私钥就在里面。
```

**"打包进去再删"是完全无效的。** 私钥进了层就永久留在层里，唯一办法是**从来不放进去**。

### ③ 原本该怎么修

```bash
# .dockerignore 里加（必须精确到文件，别整个排除 .streamlit/，config.toml 是要进镜像的）
.streamlit/secrets.toml
```

```yaml
# docker-compose.yml 里改成运行时挂载（宿主机文件映射进容器，不进镜像层）
services:
  dca:
    volumes:
      - ./.streamlit/secrets.toml:/app/.streamlit/secrets.toml:ro
```

### ④ 为什么最终选了"删掉整套 Docker"而不是上面那个修法

**因为这条问题的成因 100% 落在 Docker 那套文件里，而那套文件从来没成功跑过一次**（详见 `BUG-012`）。

```
修法 A（加 .dockerignore 一行）：成因还在 —— 只要有人写错一次 COPY，或者
                                 有人 build 时用了别的 Dockerfile，风险回来
修法 B（删掉 Dockerfile）：      没有 Dockerfile → 没有 build → 没有镜像层
                                 → 这条外泄路径在物理上不存在
```

**根除成因 > 加一道防线。** 而且被删的东西本来就是死的，删除的代价是零。

**但 `.dockerignore` 刻意保留了**，并把 `.streamlit/secrets.toml` 放在**第一条**，作为"将来谁再写 Dockerfile"时的安全默认 —— 那时候他不需要重新踩这个坑。

### ⑥ 业界通用做法

## BUG-016｜零 TLS、无自有域名

## BUG-028｜陈旧闸判的是 bar 日期，不是实时价新鲜度

| 等级 | 状态 | 发现日期 | 确认日期 | 修复日期 | 主要证据 |
|---|---|---|---|---|---|
| **P1** | ✅ **已验证** | 2026-08-20 | 2026-08-20 | 2026-08-20 | 实测 GC=F 库内 08-18 / 实时价 08-20 03:35，7 天闸放行出金额 376.74 |

- **① 现象**：2026-08-20 03:40 UTC 实测，`GC=F` 库内最后一根 bar 是 `08-18 = 4366.00`，而 `regularMarketPrice = 4554.80`（`regularMarketTime` 是 3 分钟前）——**差 4.3%**。陈旧闸判定 `stale_days=0`、`degraded=false`，照常出金额 `376.74`。更隐蔽的一层：Yahoo 挂掉走 `cache_stale` 分支时，`latest` 会静默回落成 `closes[-1]`（旧收盘价冒充实时价），输出 JSON 里**没有任何字段**说明这个值不是实时的——`fx` 段早已有 `live/as_of` 三态，行情价却没有对应物。
- **② 原理**：`market_freshness` 判的是 `history_end`（最后一根 K 线的**日期**）距 `biz_today()` 多少天，上限 7 天。但 bar 日期会因三件与"价格新不新"无关的事天然落后：休市（周末/节假日）、数据源 `close` 为 null 的空洞（见 `BUG-030`）、以及 24 小时标的的 bar 边界。真正决定"决策用的价新不新"的是 `regularMarketPrice` 与 `regularMarketTime`——引擎每次都抓到了它们（`pairs_from_chart_result` 从 `meta` 取），却只拿去算估值和 MA 偏离，没有用于判闸。
- **③ 修法**：判据换成实时价新鲜度。本次抓到 `regularMarketPrice` 即放行——休市时它等于上一收盘价，那就是**最新可得的值**，合法；没抓到（`cache_stale` 或 yfinance 兜底路径拿不到 meta）即拦，不许旧收盘价冒充实时价。另设一道宽松的序列上限，兜住"数据源长期只返回 null"这种既抓得到实时价、序列却不再前进的情形。`latest` 回落 `closes[-1]` 时必须显式标记来源，与 `fx` 的 `live/as_of` 对齐。
- **④ 为什么有效**：把判据从"代理指标"换成"被判对象本身"。bar 日期是价格新鲜度的**代理**，而代理会在休市和数据源空洞时失真——今天的 GC=F 就是活例：代理说落后 2 天（其实不该拦），被判对象说 3 分钟前（该放行），而 7 天闸两头都判错了方向。
- **⑤ 验证**：构造四种输入断言闸门行为——实时价新鲜、实时价缺失（回落 closes[-1]）、休市时实时价等于上一收盘、序列长期停滞但实时价正常；断言 `degraded` 与 `suggested_amount_rmb` 的取值，并断言 `latest` 的来源标记随分支正确翻转。
- **⑥ 业界做法**：价格服务对外一律带 `as_of` 与 `source`，消费方按 as_of 自行决定是否可用；判"数据能不能用"从不看行号或序列长度这类代理量，只看该值自己的时间戳。

#### ✅ 确认记录

> **2026-08-20 确认（用户在三选一中拍板"改判 regularMarketTime 新鲜度（推荐）"）**：
> 1. **放行判据**：本次抓到 `regularMarketPrice` → 放行，**无论 bar 多旧**（休市时它等于上一收盘价，就是最新可得值）。
> 2. **拦阻判据**：拿不到实时价 → 拦（不出金额、只展示持仓）。用户原话"不能使用昨天的值"的准确落点是这一条：不是禁止用昨天的收盘价（休市时它就是最新值），而是**禁止在拿不到实时价时用旧值冒充**。

## BUG-029｜当日实时价没有持久落点，评分是混合口径

| 等级 | 状态 | 发现日期 | 确认日期 | 修复日期 | 主要证据 |
|---|---|---|---|---|---|

- **③ 修法**（三档，待拍板）：**A 最小**——建 `src/state.py` 集中定义 11 个键名常量 + 每键标注所属链与生命周期，60 处裸字符串换成常量引用，零行为变更；**B 中等**——A 之上再封一层薄访问函数（`get_pending_tx()` / `clear_sync_flag()` 等），键名不再出现在业务代码里；**C 重**——引入统一 state dataclass，`session_state` 只存一个对象。
- **④ 为什么有效**：拼写错从"静默创建新键"变成 import 期或属性访问期立刻报错；新增一条业务链时，既有键与归属一眼可见，不必反向 grep 三个模块去猜。
- **⑤ 验证**：常量替换后 AppTest 整页无异常 + 六 tab 齐（行为零变更）；`grep` 断言业务代码里不再出现裸键字符串；`synced` 的全部 7 个读写点指向同一常量；登出后断言键池为空。
- **⑥ 业界做法**：全局可变状态集中定义（常量模块 / Enum）是最低成本的约束手段；Streamlit 官方文档亦建议用常量而非字面量书写 `session_state` 键，以避免 typo 静默建键。

## BUG-033｜最终归一化破坏权重上下界，六成评分组合越界

| 等级 | 状态 | 发现日期 | 确认日期 | 修复日期 | 主要证据 |
|---|---|---|---|---|---|
| **P2** | ✅ 已修复 | 2026-08-20 | 2026-08-20 | 2026-08-20 | 34.4 万组评分扫描：61.2% 越界，最坏 sp500 = 0.55916793（上限 0.55） |

- **① 现象**：`score_based_weights()` 收尾是「三轮（归一 → 钳位）+ 最后再归一一次」。**最后那次归一不带钳位**，于是把刚刚贴在界上的值等比缩放出界。以 `data/config.json` 的实装界（sp500 0.2/0.55、nasdaq100 0.3/0.7、gold 0.1/0.3）与 `tilt_strength=0.9` / `defense_boost=0.6` 扫描评分空间（三个评分各取 −1.0…1.0 步长 0.05、trend 取 −1/−0.5/0/0.5/1，共 344,605 组）：
  - **61.2%（210,884 组）出现越界**——不是极端角落，是常态；
  - 突破上限最坏 **+9.17e-03**：`sp500 = 0.55916793`，上限 `0.55`（评分 sp=−0.3 / ndx=−0.85 / gold=−1.0 / trend=0）；
  - 跌破下限最坏 **−3.35e-03**：`nasdaq100 = 0.29664874`，下限 `0.3`（评分 sp=−0.05 / ndx=−1.0 / gold=−0.7 / trend=−1.0）。
  > ⚠️ **登记时的两处记录错误，一并更正**：原索引行与 `BUG-015` 第 7 条备注写的 `sp500 = 0.19979818`（缺口 2e-4）**复现不出来**——以测试同一组输入（`_scores(-0.8, 0.9, -0.5, trend=0.4)` + `tests/conftest.py` 的 `assets`/`model` fixture，与 `config.json` 数值一致）实测为 `0.19993993`，缺口 `6.01e-05`；换 trend、换评分组合均无一产出 `0.19979818`，判定为登记时抄错的数。原表述「轻微越过」也不实——**在上限一侧低估了约 46 倍**，故标题同期改写。
- **② 原理**：「归一」与「钳位」是两个互相破坏的操作——归一保证 `Σw = 1` 但不管界，钳位保证界但不管和。交替迭代只是不动点近似，**没有收敛保证**，而收尾那次裸归一等于明确放弃界。危害不对称：`max_weight` 是**风控上限**（"标普最多 55%"），它被突破 0.92 个百分点意味着这条声明的保证不成立；而 `min_weight`/`max_weight` 是 `config.json` 里的公开配置项，任何将来读它并假定"实际权重必在此区间"的代码或测试都会踩空。钱上的量级：1500 元/日基准下最大偏差约 14 元，5000 元基准下约 46 元——单日不大，但它是**系统性偏移**而非随机抖动。
  > 📌 **单点测试为什么没拦住**：`test_weights_stay_inside_bounds` 恰好抽在缺口仅 `6e-05` 的那一点上，又给了 `0.01` 容差，于是缺陷被吞掉。更险的是这个容差**只比真实最坏值 `9.17e-03` 大 8%**——它不是"松了 50 倍"，是**离失效只差一点**，改动任一权重参数就会开始随机闪红。
- **③ 修法**：不再迭代，改为解一个标量 λ 使 `Σ clamp(λ·raw_i, min_i, max_i) = 1`。该和对 λ **单调不减且连续**，`λ→0` 时取 `Σmin = 0.6`、`λ→∞` 时取 `Σmax = 1.55`，因 `0.6 ≤ 1 ≤ 1.55`，由介值定理解必存在，二分即可求得。`raw` 的计算（倾斜、黄金防御加成、`neutral × 0.2` 地板）一行不改；区间容不下 1（`Σmin > 1` 或 `Σmax < 1`）时退回纯归一并保住和为 1。
- **④ 为什么有效**：`clamp` 使界成为**构造性保证**而非近似结果；`Σw = 1` 由 λ 的取值负责。两个不变量不再互相破坏，因此不存在"迭代几轮才够"的问题。
- **⑤ 验证**：见下方「验证结果」。
- **⑥ 业界做法**：带上下界的单纯形投影是标准问题，`clamp + 单调二分`（保序回归/水填充的同族解法）是最常见的实现。**施工期曾先试"水填充"（残差只分给未触界者）并被同一扫描否决**：当三资产同时越界且方向相反时（如 sp500/nasdaq100 低于下限、gold 高于上限）一次全锁死，`0.2 + 0.3 + 0.3 = 0.8`，`|Σw − 1|` 最坏达 **0.2**——界守住了却把和毁了，比原缺陷更严重（12,474 组命中）。记此一笔：**候选方案必须在同一扫描下同时验两个不变量，只验一个会选错**。

## BUG-034｜无宕机告警，外部探针未接

| 等级 | 状态 | 发现日期 | 确认日期 | 修复日期 | 主要证据 |
|---|---|---|---|---|---|
| **P2** | ⚪ **已判定不修** | 2026-08-17（随 BUG-017 登记，2026-08-21 拆出独立条目） | 2026-08-21 | — | 无任何外部探针；应用挂掉只能靠有人去开发现打不开 |

- **① 现象**：线上应用没有任何外部可用性探测，也没有告警通道。应用彻底挂掉（容器崩、平台故障、部署失败）时，唯一的发现方式是**有人去打开发现打不开**。
- **② 原理**：可用性监测必须来自系统外部——进程自己挂了就不可能上报自己挂了。项目内的日志（BUG-017）解决的是"出事后能查真因"，解决不了"出事了有人知道"。
- **③ 修法**：接一个免费外部探针（UptimeRobot 免费档 5 分钟间隔 / 50 个监控），目标 = 线上 URL，通知走邮件。**零代码改动**——应用已设 public（见 [ARCHITECTURE §1.7](../docs/ARCHITECTURE.md)），匿名 GET 即可探测。
- **④ 为什么有效**："挂了"的发现时延从"下一个想用的人打开的时刻"（最坏可达一整天）压到 5 分钟内，且发现者从人变成系统。
- **⑤ 验证**：手动停掉/改坏部署 → 5 分钟内收到告警邮件；恢复后收到 recovery 邮件。
- **⑥ 业界做法**："如果你没监控它，它就还没上线"；免费探针是个人/家庭项目的起步配置，成本为零。

#### ✅ 确认记录

> **2026-08-21 判定不修（用户拍板）。** 本条原是 BUG-017 ③"最小三件套"里的探针那半，同日拆出独立登记。理由：
>
> 1. **探针要解决的那个窗口，当前成本接近零**。用户 2026-08-21 明确："现在确实只有我一个人用。"而本应用的用法本身是**每日决策**，等于每天都有人打开——无探针时"挂了没人知道"的最长窗口约一天。这一天的代价按策略设计是可吸收的：[core-strategy §2](../strategy/core-strategy.md) 明写**跳过的金额不作废、自动摊入后续交易日**，漏投一天不减少总投入、不改变纪律。花外部依赖去压缩一个代价≈0 的窗口，不合算。
> 2. **探针买到的能力比直觉窄得多，恰好错过真正会疼的失效**。HTTP 200 探针只能发现"整个应用不可达"，发现不了"应用活着但坏了"。反例就在代码里：云端存储读不出名单时，[src/ui/auth.py:309-312](../src/ui/auth.py) 渲染一句"☁️ 云端存储暂时不可用"再 `st.stop()`——这是一个**正常返回的 200 页面**，探针全绿；行情降级（`degraded`）时同样照常出页面。也就是说：探针挡不住的，正是 BUG-017 日志半要留痕的那些。
> 3. **副作用要一并接受**。Streamlit Community Cloud 免费档应用长期无访问会进休眠页；5 分钟一探等于让它永不休眠。对使用体验是好事，但这是把探针当保活用，与"监控"是两码事，且休眠页的 HTTP 状态码若为 200，探针对休眠本身同样失明（**未实测**）。
>
> **触发重开条件**（任一成立即翻回 🔴 重新确认）：① 家人或第二个人真的开始日常使用（届时"每天有人打开"不再等价于"用户本人当天会发现"，且旁人遇到挂掉不一定会说）；② 用户不再每天打开决策台；③ 应用从家庭自用转为对外服务。
>
> **一处过程更正（留档，避免下次再犯）**：施工方最初建议判不修，理由写的是"只有用户一人使用"——**这条当时未经核实**。随后在仓内读到多处"应用设成 public，否则家人打不开"（[BUG-003](#bug-003认证门闸形同虚设)、[BUG-016](#bug-016零-tls无自有域名)、[ARCHITECTURE §1.7](../docs/ARCHITECTURE.md)），据此反过来判定该前提为假、把本条改登记为开放项。**两次都错在取证来源**：那些记载说的是**设计意图与访问配置**（设成 public 是为了家人**能**打开），不是**当前实际使用情况**；后者的权威来源只有用户本人，经其确认后前提成立，判定回到不修。
