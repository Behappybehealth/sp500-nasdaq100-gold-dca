## 1.2 理解一切的钥匙：Streamlit 的"脚本重跑"模型

这一点必须先弄懂，因为后面**至少三个 P0 问题都源于它**。

传统网页框架（Flask/Django）是这样：你写一堆"函数"，用户访问哪个网址就调用哪个函数。函数之间互不干扰。

**Streamlit 完全不同：**

```
用户第一次打开页面
   → 服务器从第 1 行开始，把 app.py 整个文件执行到最后一行
   → 执行过程中每遇到 st.xxx() 就往页面上画一个东西

用户点了一下按钮/滑块/输入框
   → 服务器又从第 1 行开始，把 app.py 整个文件重新执行一遍
   → 重画整个页面
```

**打个比方**：像一个厨师，你每换一次口味要求，他不是只改那一步，而是**把整本菜谱从第一页重念一遍**，只是这次在某一页做了不同的选择。

这个模型带来三个必然的后果，Streamlit 用三个机制来应付：

| 问题 | Streamlit 的机制 | 项目里怎么用的 |
|---|---|---|
| 重跑一遍，之前用户填的东西不就丢了？ | **`st.session_state`** —— 一个字典，跨"重跑"活着，每个浏览器标签页各有一份 | 存登录状态 `user`、待确认的记账 `pending_tx` 等 11 个键 |
| 重跑一遍，慢操作（抓行情、算模型）每次都重做？ | **`st.cache_data`** —— 记住函数的结果，下次同样参数直接返回 | `run_model()` 缓存 900 秒 ← **P0-1 就出在这里** |
| 重跑一遍，怎么让页面停在登录页不往下走？ | **`st.stop()`** —— 立刻停止本次执行 | 认证门闸用它拦住未登录用户 ← **P0-2 出在这里** |

**关键点：`st.session_state` 是"每个浏览器一份"，但 `st.cache_data` 是"整个服务器共用一份"。** 这个区别是 P0-1 的全部原因。

## 1.3 为什么计算用"子进程"（subprocess）

`app.py` 自己不算策略。它是这样做的：

```
app.py  ──启动一个全新的 Python 程序──→  scripts/dca_calculator.py
        ←──── 对方把结果打印成 JSON 文字 ────
        （app.py 读这段文字，转成数据用）
```

用代码看就是 [app.py:558-572](app.py#L558-L572)：

```python
cmd = [sys.executable, "scripts/dca_calculator.py", "--base-dir", str(BASE)]
out = subprocess.run(cmd, capture_output=True, timeout=180)
return json.loads(out.stdout)          # 把对方打印的 JSON 转成 Python 字典
```

**打个比方**：不自己做饭，打电话叫外卖。好处是厨房（引擎）和餐厅（UI）完全隔离——改菜谱不会弄坏餐厅装修。这个设计是**对的**，也是这个项目最干净的一处。

代价是：两边只能通过"命令行参数"和"打印出来的文字"沟通。引擎不知道谁是当前用户，它只知道 `--base-dir` 指向哪个目录、那个目录里的 CSV 写了什么。**这是 P0-1 的另一半原因。**

## 1.4 为什么用 Google Sheets 当数据库

好处很实在：不用买服务器、不用装数据库、你能用手机打开表格直接看数据、免费。

代价是**它没有"改一行"的能力**。真正的数据库你可以说"把第 5 行的金额改成 1000"。Google Sheets 这套库只能：

- 读：把**整张表**拉下来
- 写：把**整张表**推上去（覆盖）

所以"加一笔成交记录"的实际动作是（[storage.py:304-306](storage.py#L304-L306)）：

```
把整张 transactions 表读下来（比如 200 行）
  → 在末尾拼上你这 1 行（变 201 行）
  → 把这 201 行整体推上去，覆盖原来的 200 行
```

**打个比方**：改一个字，要把整本书重新抄一遍再交上去。**这是 P0-3 的全部原因**——如果"读下来"这一步失败了，你手里就是一本空书，抄完交上去，原来那本就没了。

```

      ↓
② storage.authenticate() 去 Google Sheets 的 users 表比对 PIN 的哈希值
      ↓ 通过
③ storage.sync_local(用户名)
      把 Google Sheets 里【这个用户】的成交记录，写成本地 data/transactions.csv
      ↑↑↑ 注意：写的是同一个文件路径，不分用户  ← P0-1 的根源
      ↓
④ 侧边栏调用 run_model(None)
      → 启动子进程 dca_calculator.py --base-dir <项目目录>
      ↓
⑤ 引擎读 data/transactions.csv（刚才写的）+ data/config.json
      → 增量抓行情（只抓缓存里缺的那几天）
      → 算评分、算金额、算比例
      → 把结果 print 成一大段 JSON
      ↓
⑥ app.py 收下 JSON，拆成 result / dec / ms / pf 四个变量
      → 结果被 st.cache_data 缓存 900 秒，缓存键只有「金额」  ← P0-1 的另一半
      ↓
⑦ 6 个 Tab 依次渲染，直接用上面那四个变量
      ↓
⑧ 用户在 Tab3 回报成交 → storage.append_row() 写回 Google Sheets
```

# 第四部分：五个 P0 问题详解

每条都按同一个结构讲：**现在会发生什么 → 为什么 → 怎么修 → 为什么这么修有效 → 修完怎么验证 → 业界通用做法**。

---

## P0-1 ｜跨用户数据串号

### ① 现在会发生什么

用户 A 登录看完今日建议，15 分钟内用户 B 登录 —— **B 看到的持仓、市值、浮盈亏、年化收益、今日建议金额，全都是 A 的。**

不是"泄露一点点"，是 B 的整个决策建立在 A 的持仓上。B 会照着这个金额真去下单。

### ② 为什么会这样

**两个独立原因，任一个都足以串号。**

**原因一：缓存是"整个服务器共用一块白板"**

```python
app.py:556   @st.cache_data(ttl=900, show_spinner=False)
app.py:557   def run_model(amount: float | None) -> dict:
```

`@st.cache_data` 的意思是"记住这个函数的结果，900 秒内同样参数直接返回"。它判断"同样参数"的依据，**只看函数的参数列表** —— 这里只有 `amount`。

```
A 调用 run_model(None) → 算出 A 的结果 → 记到白板上，标签写「None」
B 调用 run_model(None) → 一看白板上有「None」→ 直接把 A 的结果抄给 B
```

**关键**：`st.session_state`（存登录状态那个）是**每个浏览器一份**，但 `st.cache_data` 是**整个服务器进程共用一份**。这个区别很容易搞混，也正是问题所在。

**原因二：所有用户共用同一个数据文件**

```python
app.py:26-34    BASE = --base-dir 指定的目录，没指定就是项目目录
                DATA_DIR = BASE / "data"
                ↑ Cloud 上没人传 --base-dir，所以所有用户都是同一个 data/ 目录
storage.py:368  sync_local(user)：把这个用户的成交记录写进 data/transactions.csv
```

A 登录时把 A 的账本写进这个文件；B 登录时把它**整体覆盖**成 B 的账本。两人同时在线，就是两个子进程在读一个正在被对方覆写的文件。

### ③ 怎么修

**必做（小改动，堵住原因一）**：让缓存键包含用户身份。

```python
# 现在：缓存键 = (amount)
@st.cache_data(ttl=900)
def run_model(amount): ...

# 改成：缓存键 = (amount, user, data_dir)
@st.cache_data(ttl=900)
def run_model(amount, user, data_dir): ...      # user/data_dir 参与键，即使函数体不直接用
```

**该做（堵住原因二）**：每个用户一个数据目录。

```
data/
├── users/
│   ├── alice/transactions.csv      ← A 的账本
│   └── bob/transactions.csv        ← B 的账本
└── market_history/                 ← 行情缓存共享（这个共享是对的，行情对所有人一样）
```

然后 `run_model` 传 `--base-dir data/users/<用户名>`。

### ④ 为什么这么修有效

**缓存的第一原则：缓存键必须包含所有会影响结果的输入。**

现在"用户身份"影响结果，却不在键里 → 系统认为"参数一样，结果就该一样" → 必然串号。把用户加进键，A 和 B 就是两个不同的格子，各存各的。

**数据目录分开的原理**：两个进程写同一个文件必然竞争，写不同文件就不会。行情缓存留在共享位置是**刻意的**——行情对所有人是同一个事实，共享既省流量又省磁盘。

### ⑤ 修完怎么验证

1. A 登录记一笔特征明显的成交（比如 12345 元），退出
2. 30 秒内 B 登录 → **B 的持仓里不应出现 12345**
3. 检查磁盘：`data/users/` 下应有两个目录，各自 CSV 内容不同
4. 反复交替登录 5 次，两人数字始终各自独立

### ⑥ 业界通用做法

这是**多租户系统**（一套程序服务多个客户）的入门必修课，标准做法两条：

- **缓存按租户隔离**（tenant-scoped cache）：任何缓存键都必须带租户 ID。大厂的缓存库通常强制要求传租户上下文，就是为了防这个。
- **数据按租户隔离**：轻量做法是"一租户一目录/一 schema"，重量做法是"每行带 tenant_id 且所有查询强制过滤"。这个项目在 Sheets 层用了后者（每张表有 `user` 列），但在**本地缓存文件层漏了** —— 一半做对了，另一半没做。

## P0-2 ｜认证是 fail-open 的（门闸可以整体消失）

### ① 现在会发生什么

正常时：打开网页 → 要求输入名字和 PIN → 通过才进主界面。

**但如果读取凭据这一步出任何问题** → 登录页**完全不出现**，任何人打开网址直接进主界面，身份是 `"local"`。页面上看不出任何异常，没有任何报错和日志。

### ② 为什么会这样

```python
app.py:430   CURRENT_USER = "local"
app.py:431   if storage.sheets_enabled():        ← 整个登录门闸在这个 if 的里面
                  ... 名字+PIN 校验 ...
                  st.stop()                       ← 没登录就停在这里
             # if 结束，下面是主界面
```

而这个开关是：

```python
storage.py:63-68   def sheets_enabled():
                       try:
                           return "gsheets" in st.secrets.get("connections", {})
                       except Exception:
                           return False           ← 出任何岔子都返回「关」
```

`try / except Exception: return False` 的意思是"不管出什么错，都当作没配凭据"。而"没配凭据"在这个项目里等于"单机模式，不需要登录"。

**打个比方**：门禁系统的逻辑写成了"如果读卡器坏了，就当今天不需要刷卡"。断电之后门是**自动打开**的。

这在安全工程里有专门的名字：**fail-open**（失效即放行）。反面是 **fail-closed**（失效即拦住）。

### ③ 怎么修

加一个显式的"我要求哪种模式"配置，然后在**程序启动时就检查**：

```python
# 大意（不是最终代码）
AUTH_MODE = 读配置("AUTH_MODE", 默认="sheets")     # sheets | local

if AUTH_MODE == "sheets":
    if not storage.sheets_enabled():
        st.error("配置错误：AUTH_MODE=sheets 但读不到 Google 凭据。已停止。")
        st.stop()                                  # 拦住，不降级
    # 往下必然走登录门闸
elif AUTH_MODE == "local":
    CURRENT_USER = "local"                         # 明确的单机模式，是你选的
```

同时把 `sheets_enabled()` 里的 `except Exception: return False` 改成**区分两种情况**：
- "配置里确实没有 gsheets 这一项" → 返回 False（正常的单机模式）
- "读配置时抛异常" → 抛出去，让上层知道出事了

### ④ 为什么这么修有效

核心是把**一个隐式推断**换成**一个显式声明**。

现在的逻辑是"我猜你想要什么模式"（猜的依据是文件在不在）。改完是"你必须告诉我要什么模式，然后我检查你给的东西够不够，不够就罢工"。

这叫 **fail-closed**：安全控制失效时，朝着"更安全"的方向倒。门禁断电应该是锁死，不是敞开。

配合的第二个原则是 **fail fast on startup**（启动即校验）：配置问题应该在程序启动的第一秒暴露，不要等到运行时才以奇怪的方式表现出来。

### ⑤ 修完怎么验证

1. 正常配置下启动 → 出现登录页 ✅
2. **故意**把 secrets 里的 `[connections.gsheets]` 改名成 `[connections.gsheetsX]` → 启动应该**立刻报错停住**，而不是进主界面
3. 明确设 `AUTH_MODE=local` → 直进主界面，且页面上有明显的"单机模式"提示

### ⑥ 业界通用做法

- **Secure by default / fail-closed**：安全机制的默认值和失效方向都应偏向"拒绝"。这是 OWASP 反复强调的第一条。
- **启动期配置校验**（config validation at boot）：把所有必需配置在启动时校验一遍，缺了就拒绝启动。Kubernetes 里叫 readiness probe 失败，12-factor 应用叫 "fail fast"。
- **绝不用「文件是否存在」推断安全策略**：策略必须是显式声明的，环境的偶然状态不能改变安全模型。

## P0-3 ｜一次读取失败 = 全部历史被覆盖

### ① 现在会发生什么

Google 那边抖一下（返回 503、配额超了、凭据过期、网络闪断），紧接着你记一笔账 —— **整张成交记录表被这一笔覆盖，几百条历史全没了。而且没有备份可以恢复。**

第二种触发方式更糟：读取失败让系统以为"一个用户都没有" → 登录页变成"首次注册"表单 → 任何访客注册即成为管理员，同时把 users 表覆盖成只有他一行 → **所有账号消失**。

### ② 为什么会这样

回到 1.4 讲的：Google Sheets 只能"整张表读下来 / 整张表推上去"。

```python
storage.py:299-307   def append_row(...):
                         df = _read_ws(table, fields)      # ① 读整张表
                         df = concat([df, 你这一行])        # ② 拼上你的
                         _write_ws(table, df)              # ③ 整张推回去
```

问题在第 ① 步：

```python
storage.py:107-110   try:
                         df = _conn().read(worksheet=name, ttl=0)
                     except Exception:
                         return pd.DataFrame(columns=fields)    ← 失败也返回一张空表
```

**"读失败"和"表本来就是空的"，返回的是同一个东西 —— 一张空表。** 上层完全无法区分。

于是：读失败 → 手里一张空表 → 拼上你这一行 → 推回去 → **原来 200 行被 1 行覆盖**。

**打个比方**：让你抄书。你去取原书，图书馆没开门，你手上是白纸。你在白纸上写了一句话，交回去当作新版本 —— 原书被销毁了。

**为什么"防呆"没用**：登录那条路上确实有一道检查（[app.py:507-510](app.py#L507-L510) 提交时再读一次用户名单）。但读取还在失败，第二次读到的**还是空** → 检查通过 → 照样覆盖。这道防呆只防"缓存过期"，不防"读失败"。

**为什么备份救不了**：

```python
storage.py:378-380   if path.exists() and not 备份文件.exists():     ← 只在备份不存在时才备份
                         path.replace(备份文件)                      ← 而且是「移动」不是「复制」
```

- 条件是"备份**不存在**时才备份" → 备份只在第一次同步时生成过一次，之后永远是最早那一份
- 用的是 `replace()`（移动/重命名），原文件消失 → 紧接着重新写出。如果在这两步之间崩掉，当前文件就没了
- **而且这只备份本地缓存 CSV。真正的数据在 Google Sheets，项目没有自动导出、命名快照、保留周期或恢复演练；平台版本历史可能是最后一道救命绳，但不能替代项目自己的备份制度**

### ③ 怎么修

**三层，从最小改动往上：**

**第一层（必做，改动最小）—— 让失败可区分**

```python
def _read_ws(name, fields, fresh=False):
    try:
        df = _conn().read(worksheet=name, ttl=0)
    except Exception as e:
        raise StorageReadError(f"读取 {name} 失败：{e}") from e   # 抛出去，不再假装是空表
```

然后调用方分情况处理：
- `append_row` 遇到这个异常 → **绝不写入**，向用户显示"云端暂时读不到，请稍后再试"
- `list_users` 遇到 → 显示"服务暂时不可用"，**绝不进入首次注册流程**

**第二层（该做）—— 写之前留一份快照**

每次整表覆写前，先把当前内容复制到一个 `xxx_backup` 工作表或加时间戳的备份区。写坏了能回滚。

**第三层（更稳）—— 加一个"行数不该突然变少"的闸**

```python
if len(新表) < len(旧表) and 不是明确的删除操作:
    拒绝写入并告警
```

顺便把 `.localbak` 改成：**复制**而非移动，带时间戳，保留最近 N 份。

### ④ 为什么这么修有效

核心原则：**错误和空值必须可区分**。

现在的代码把"我不知道"和"我知道，是空的"压成了同一个返回值。**信息一丢失，后面所有判断都是错的** —— 这不是哪一处逻辑写错，是接口设计缺了一个状态。

Python 里表达"操作失败"的标准方式就是**抛异常**。`except Exception: return 空值` 这个写法叫"吞异常"，是最常见的严重反模式之一：它让错误静默传播，等到很远的地方才以完全无关的形式爆出来（这里是"数据被清空"）。

第二层"写前快照"对应的原则是：**破坏性操作前先留退路**。整表覆写就是破坏性操作。

第三层"行数不减"是一个**不变量检查**（invariant check）：账本只会增长，如果一次写入让它变短，几乎一定是 bug。

### ⑤ 修完怎么验证

1. **主动模拟失败**：临时改坏 spreadsheet 地址 → 尝试记账 → 应看到明确报错，且 Sheets 里数据**一行不少**
2. 同样条件下打开首页 → 应显示"服务不可用"，**不应出现"首次注册"表单**
3. 恢复正常 → 记一笔 → 表里应是 `原行数 + 1`
4. 检查备份工作表 / 备份文件里有可用的上一版

### ⑥ 业界通用做法

- **不要吞异常**（don't swallow exceptions）。要么处理，要么往上抛。绝不能"出错就返回一个看起来正常的值"。
- **读-改-写要有并发保护**：正规做法是版本号/乐观锁 —— 读的时候记下版本，写的时候声明"我基于版本 N 改的"，服务端发现版本变了就拒绝。Sheets 没有这个能力，所以只能靠"备份 + 不变量检查"补。
- **破坏性操作前备份**，且备份要**自动、滚动、可验证**。"只备份一次的备份"和没有备份是一样的。
- **不变量检查**：对关键数据加"只增不减"这类断言，能拦住绝大多数灾难性写入。

## P0-4 ｜Google 私钥会被打进 Docker 镜像 —— ✅ 2026-08-17 已解决

> **解决方式不是"修"，是"删"。** `deploy/Dockerfile` 等 5 个文件已删除（它们从未成功构建过一次）。
> **没有 Dockerfile → 没有 build → 没有镜像 → 私钥根本没有这条外泄路径。**
> 比修更彻底：代码路径不存在，就不可能从那里漏。
> `.dockerignore` 刻意保留并把 `.streamlit/secrets.toml` 列在第一条，作为"将来谁再写 Dockerfile"的安全默认。
>
> 下面的原理部分保留，因为**将来重启 Docker 时必须懂这个**，否则会原地再踩一次。

### ① 原先会发生什么

任何人（包括你自己）在这台开发机上执行 `docker build`，构建出的镜像里就**包含完整的 Google 服务账号私钥**。镜像一旦推到任何仓库、导出成文件发给别人、或者被别人拉下来 —— **拿到私钥的人可以读写你的整个 Google 表格**（所有用户的持仓和金额）。

### ② 为什么会这样

先解释两个概念：

- **`.gitignore`**：告诉 git "这些文件不要提交"。**只管 git。**
- **`.dockerignore`**：告诉 docker "构建镜像时这些文件不要打包进去"。**只管 docker。**

**这是两个完全独立的清单。** 项目里 `.gitignore` 正确排除了 `secrets.toml`，但：

```
.dockerignore 全文只有 8 行：
   data/  __pycache__/  *.pyc  .git/  .claude/  backtest*/  *.md  !deploy/
   ↑ 没有 .streamlit/

deploy/Dockerfile:21    COPY .streamlit/ .streamlit/      ← 整个目录打包进去

开发机实况              .streamlit/secrets.toml 确实存在，2600 字节，含真实私钥
```

**更麻烦的是 Docker 镜像的分层机制**：镜像像地质层，每条指令堆一层。你在后面的层里 `rm` 掉这个文件，**前面那层里它还在**，用工具能挖出来。所以"打包进去再删"是无效的。

### ③ 怎么修

**第一步（一行，立刻）—— 排除掉**

```
# .dockerignore 里加
.streamlit/secrets.toml
```

**第二步 —— 改成运行时提供，而不是构建时打包**

凭据应该在**容器启动时**从外部给进去，不进镜像：

```yaml
# docker-compose.yml 里挂载（宿主机文件映射进容器，不进镜像层）
volumes:
  - ./secrets/secrets.toml:/app/.streamlit/secrets.toml:ro
```

（Streamlit Community Cloud 已经是对的做法 —— 凭据填在平台后台，不在代码里。）

**第三步 —— 如果镜像已经构建并分享过，轮换密钥**

去 GCP 控制台把这个服务账号的密钥作废、生成新的。**私钥一旦可能泄漏，唯一的补救是换掉它**，不是"希望没人看到"。

### ④ 为什么这么修有效

原则是**密钥与代码分离**（在 12-factor 应用方法论里叫 "config in the environment"）：

- 代码/镜像是**可以到处传播**的东西（推仓库、发同事、放 CI）
- 密钥是**绝不能传播**的东西
- 所以两者必须在不同的载体里。密钥通过环境变量或运行时挂载注入，镜像本身不含任何密钥

这样同一个镜像可以安全地在开发/测试/生产跑，区别只在于外面注入什么凭据。

### ⑤ 修完怎么验证

```bash
# 构建后检查镜像里到底有没有这个文件
docker run --rm <镜像名> ls -la /app/.streamlit/
# 期望：只有 config.toml，没有 secrets.toml

# 更彻底：搜所有镜像层
docker save <镜像名> -o img.tar && tar tf img.tar | grep secrets
# 期望：零命中
```

### ⑥ 业界通用做法

- **密钥永不进版本库、永不进镜像层**。这是硬规则。
- 注入方式按环境：本地用 `.env`（gitignore 掉）；容器用运行时挂载或 `--secret`；云平台用平台的 secrets 管理（Streamlit Cloud 后台 / AWS Secrets Manager / GCP Secret Manager）
- **假设泄漏就当已泄漏**：判断标准不是"有没有人真的看到"，而是"有没有可能被看到"。可能了就轮换
- CI 里加密钥扫描（gitleaks、trufflehog 之类），把这类问题拦在提交前

## P0-5 ｜PIN 的保护强度撑不住公开部署

### ① 现在会发生什么

应用是公开的（任何人知道网址就能打开登录页），而登录页的**用户名是下拉框，直接列出所有人**。攻击者只需猜 PIN。

PIN 只要 4 位，且**没有任何失败次数限制** —— 可以无限次尝试。4 位纯数字只有 1 万种组合。

另外，存在表里的 `pin_hash` 如果泄漏（表被误分享、协作者、或者通过 P0-3/P0-4 的路径），**几乎等于明文** —— 原因见下。

### ② 为什么会这样

先解释**哈希**：一种单向变换。把 `1234` 变成一串固定长度的乱码，能正着算不能倒着算。所以数据库里存哈希而不是原文，被偷了也看不出原始 PIN —— **理论上如此**。

破解方式是**穷举**：把 `0000` 到 `9999` 全部算一遍哈希，跟偷到的值比对，中了就是它。所以哈希的安全性取决于**算一次要多久** × **要算多少次**。

这个项目的实现：

```python
storage.py:134-135   def _pin_hash(name, pin):
                         return sha256(f"dca::{name}::{pin}").hexdigest()
```

三个问题叠在一起：

| 问题 | 说明 |
|---|---|
| **SHA256 是"快哈希"** | 它是为"快速校验文件完整性"设计的，一台普通显卡每秒能算**几十亿次**。1 万种 PIN 组合 → **不到千分之一秒穷举完** |
| **只算一轮** | 密码哈希的标准做法是故意重复几十万次让它变慢。这里只算 1 次 |
| **"盐"是用户名，而用户名是公开的** | "盐"（salt）是给每个用户加的随机料，作用是让攻击者不能一次性算好一张万能对照表。这里用用户名当盐 —— 而用户名在登录页下拉框里公开可见，等于盐是已知的，防护效果大幅削弱 |

再加上**没有失败限速**（全项目 grep `attempt`/`lockout`/`rate_limit` 零命中），在线爆破也是可行的：1 万次请求，即使每次 1 秒也就 3 小时。

### ③ 怎么修

**三件事，都是标准动作：**

**(1) 换成"慢哈希"**

```python
# 现在：一次 SHA256，快得像闪电
sha256(f"dca::{name}::{pin}")

# 改成：PBKDF2 高迭代（Python 标准库自带，无需新依赖）
import hashlib, os
salt = os.urandom(16)                                    # 每个用户一份独立随机盐
key  = hashlib.pbkdf2_hmac("sha256", pin.encode(), salt, 200_000)
# 存 salt 和 key 两个字段
```

`200_000` 表示重复 20 万次。对用户来说是几十毫秒（察觉不到），对攻击者来说穷举速度慢了 20 万倍。如果愿意加依赖，`argon2` 或 `bcrypt` 更好。

**(2) 加失败限速**

在 users 表加两列 `fail_count` / `locked_until`：连续错 5 次锁 15 分钟。

**(3) PIN 位数下限从 4 提到 6，并且不再公开完整用户名单**

登录页改成手动输入名字，不给下拉框 —— 攻击者得同时猜名字和 PIN。

### ④ 为什么这么修有效

三条互相独立、叠加起效：

- **慢哈希**解决"偷到哈希后离线穷举"。原理是把攻击成本乘以迭代次数。用户登录一次多花 30 毫秒，攻击者穷举多花 20 万倍时间 —— **这个不对称是密码哈希的全部设计意图**
- **独立随机盐**解决"一张对照表打穿所有用户"。每个人盐不同，攻击者必须逐个用户单独穷举
- **失败限速**解决"在线爆破"。哈希再慢也拦不住有人一次次试，限速才拦得住
- **不公开名单**把搜索空间从"1 万"扩大到"名字空间 × 1 万"

### ⑤ 修完怎么验证

1. 新注册一个用户 → 表里应有独立的 `salt` 和迭代后的 `hash`，且**两个用同样 PIN 的用户哈希值不同**（证明盐生效了）
2. 连续输错 5 次 → 第 6 次应被拒绝并提示锁定时间，**即使 PIN 输对了也进不去**
3. 老用户平滑过渡：首次用旧哈希验证成功后，立刻用新算法重算并写回（这叫**渐进式迁移**，不用强迫所有人改 PIN）
4. 登录耗时增加应在 100 毫秒以内，用户感觉不到

### ⑥ 业界通用做法

- **密码/PIN 存储只用慢哈希**：argon2id（首选）、bcrypt、scrypt、PBKDF2（标准库就有，最容易落地）。**绝不用** MD5/SHA1/SHA256 单轮 —— 这是 OWASP Password Storage 里的明文规定
- **每条记录一个独立随机盐**，盐不需要保密但必须唯一且随机（绝不用用户名、邮箱这类可预测值）
- **失败限速 + 账号锁定 + 告警**，通常再配 IP 级限流（这个项目的 nginx 也没有限流，可以一起加）
- **短 PIN 只在有别的因素护着时才可接受**（比如手机银行的 6 位密码背后有设备绑定 + 服务端限速 + 短信验证）。裸露在公网上的 4 位 PIN 没有护栏 —— 要么加位数，要么加因素
